# Production Sanitation — Dependency Analysis

**Project TITAN — Production Sanitation & Commercial Readiness, Phase 3**
**For every deletion/archive candidate from Phase 2: who generates it, who consumes it, and across
which dependency axis (runtime/build/CI/deployment/Cloudflare/Worker/dashboard/customer).**
**The headline result of this phase: the "obvious" cleanup target (old reports) is the riskiest
one, and the "boring" targets (tracked node_modules, root-level orphan files) are the safest.**
This is exactly the kind of finding this phase exists to catch before Phase 7 finalizes a plan.

---

## 1. `workers/intel-gateway/node_modules/` — CONFIRMED SAFE TO REMOVE FROM GIT

- **Generator**: `npm install`, run locally by any developer. Never generated by CI.
- **Consumer, verified**: `deploy-worker.yml` does **not** run `npm ci`/`npm install` against this
  package's own `node_modules` — it installs `wrangler@3` and `esbuild` **globally**
  (`npm install -g wrangler@3`, `npm install -g esbuild`, `deploy-worker.yml:163,268`) and bundles
  from `workers/intel-gateway/src/` directly. No workflow step reads from the committed
  `node_modules/` path.
- **Runtime dependency**: none — Cloudflare Workers execute the esbuild-bundled output, not raw
  `node_modules` content.
- **Build dependency**: none, per the above — the actual build tool is a global install.
- **CI dependency**: none confirmed by direct grep across `.github/workflows/*.yml`.
- **Deployment/Cloudflare/Worker dependency**: none — `wrangler deploy` ships the bundle, not
  `node_modules`.
- **Dashboard/customer dependency**: none — not a customer-facing artifact.
- **Conclusion**: **zero identified dependency of any kind.** Safe to remove from git tracking
  (not from disk — `npm install` regenerates it locally for any developer who needs it; only its
  presence *in the repository* is the finding).

## 2. `data/.manifest_backups/` — NOT safe to blanket-delete; needs a retention policy, not removal

- **Generator**: not fully traced to a single script in this pass, but `scripts/safe_git_commit.py`
  builds an in-memory `_manifest_backups` structure during its own run (a variable name collision
  with the directory, not proof of a direct read/write relationship to the 35 historical files) —
  the actual writer of the 35 on-disk files was not conclusively identified and should not be
  assumed to be `safe_git_commit.py` without further confirmation.
- **Consumer, verified**: `scripts/validate_intel_schema.py` (line 467-469) checks
  `data/.manifest_backups` as one of several **candidate paths** when looking for *a* manifest
  backup — reads for existence/latest, not confirmed to require all 35 historical snapshots.
  `scripts/sanitize_repo.py` (line 76) lists `.manifest_backups`/`manifest_backups` in what reads as
  an exclusion list for its own JSON-sanitization sweep (skips validating backup files, does not
  depend on their contents).
- **Conclusion**: **real, live references exist to this path as a category**, but none of them
  were confirmed in this pass to require the *entire* 35-file history — consistent with "keep the
  most recent N" being a safe policy, "delete the directory entirely" is not confirmed safe.
  Revised from Phase 2's DELETE recommendation to **retention-policy-governed ARCHIVE** (see
  `RETENTION_POLICY.md`).

## 3. `reports/2026/07/` (prior-month reports) — NOT safe to move/archive without a coordinated step

- **Generator**: `scripts/report_generator.py`, run by `sentinel-blogger.yml`.
- **Consumer, verified and significant**: **`api/feed.baseline.json` contains 292 path references
  into `reports/2026/07/`; `api/feed.gold.json` contains 38 unique such references.** These are
  live, currently-servable API feed variant files (`api/feed.gold.json`, `api/feed.baseline.json`,
  `api/feed.silver.json`, `api/feed.standard.json` — the audience-tiered feeds documented in
  Stage 21/22's commercial audits). If these HTML files are moved or made inaccessible at their
  current path without updating the referencing feed JSON, **real customers following a served link
  from these feeds would get a 404.**
- **Deployment/Worker dependency**: `index.js` serves `/reports/**` directly from this path
  (`TITAN_V200_RELEASE_AUDIT.md` §2/§6) — moving files here is a live-route-affecting change, not a
  pure storage operation.
- **Conclusion**: **this is the single highest-risk candidate in the entire inventory**, precisely
  because it is also the single largest storage contributor. Any retention policy that removes these
  files from their served path must either (a) regenerate/update the referencing `api/feed.*.json`
  files in the same operation, (b) compress-in-place rather than move (preserving the URL), or
  (c) be scoped to exclude any report still referenced by a live-served feed variant. Phase 5/7 must
  design around this constraint explicitly — it is not a detail to patch in later.

## 4. Root-level orphan files — safe to archive

`DASHBOARD-OVERVIEW-LIVE-VIDEO.mp4`, `v55.2-complete.patch`, `SENTINEL_APEX_v78_P0_FIX.tar.gz`,
`0001-SENTINEL-APEX-v28.0-FORTRESS-Security-Hardening-Rele.patch`, `claude-tasks-history-screenshot.jpg`:

- **Generator**: one-time historical additions (single commit, 2026-08-04).
- **Consumer**: **none found** — zero references across `.html`/`.js`/`.md`/`.py`/`.yml` (re-verified
  in this phase with a second, independent grep pass beyond Phase 1's).
- **Runtime/build/CI/deployment/Worker/dashboard/customer dependency**: none identified on any axis.
- **Conclusion**: safe to archive (move out of the active tree into a clearly-labeled archive
  location, preserving git history — not a permanent deletion recommendation, per this effort's
  "reversible" principle).

## 5. `data/simulations/*.bat`, `data/products/*.zip` — CONFIRMED KEEP, no further action

- **Generator**: real product-generation scripts (not fully traced to a single script in this pass,
  but content and naming pattern — "Purple Swarm" BAS scripts, dated product archives — are
  consistent with intentional commercial output, not build byproducts).
- **Consumer**: presumed customer-facing (product deliverables), consistent with the detection-pack
  business model documented in Stage 21/22. Not confirmed served by a live route in this pass, but
  the burden of proof for deletion was not met, and per this effort's absolute rule, that alone is
  sufficient to classify KEEP without further investigation being required.

## 6. `threat/`, `syndicate/`, `data/archive/`, `data/intelligence/` — CONFIRMED KEEP

Already established as live, wired, actively-managed production paths in Phase 1/2 — re-confirmed
here, no new findings.

## Dependency analysis summary

| Candidate | Safe to touch? | Action |
|---|---|---|
| Tracked `node_modules/` | **Yes — zero dependencies found** | DELETE (from git only) |
| `data/.manifest_backups/` | Partially — category is referenced, full history is not | Retention policy (keep recent N), not blanket deletion |
| `reports/2026/07/` | **No — not without a coordinated feed-reference update** | Excluded from this cleanup pass's execution scope; requires its own follow-on effort that updates `api/feed.*.json` in the same operation |
| Root-level orphan files | Yes — zero dependencies found | ARCHIVE |
| `data/simulations/`, `data/products/` | No — real product data | KEEP, no action |
| `threat/`, `syndicate/`, `data/archive/`, `data/intelligence/` | No — live production paths | KEEP, no action |
