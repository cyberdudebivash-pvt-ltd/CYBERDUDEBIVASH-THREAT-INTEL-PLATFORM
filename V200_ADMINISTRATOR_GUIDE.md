# Administrator Guide — v200

**Project TITAN Stage 22 Phase 8**

## Admin API

`/api/admin/*` (`index.js:1708`), gated by `X-Admin-Key` header verified with `timingSafeEqual`
(constant-time comparison — correct practice against timing side-channels), 403 otherwise. The
admin key is a Cloudflare-bound secret (`env.ADMIN_SECRET`), never stored in the repository
(`SECURITY_CERTIFICATION.md` §11).

## Provisioning and revoking API keys

Keys are provisioned automatically on payment (`provisionApiKey()`, `index.js:2421`) or manually via
the admin API. **Before relying on key expiry to actually end a customer's access at the end of
their billing period**, read `COMMERCIAL_READINESS.md` §6: the expiry-enforcement fix exists in code
but is gated behind `env.SUBSCRIPTION_EXPIRY_ENABLED`, which is `"false"` in the committed
`wrangler.toml`. If this has not been separately enabled in the live Cloudflare dashboard, every
provisioned key currently grants indefinite access regardless of billing cycle. Confirm the actual
live value of this variable before making any operational assumption about expiry behavior.

## Feature flags

Two independent flag systems exist, and administrators should not confuse them:
1. **Commercial tier flags** (`TIERS` + `revenue-enforcement.js`) — live, in production, control
   customer-facing feature access. This is what actually gates the product.
2. **Gateway-lineage flags** (`EIG_FLAGS`/`KP_FLAGS`/`PP_FLAGS`/`CC_FLAGS`) — internal, scoped to
   the unwired `enterprise-gateway`/`knowledge-platform`/`product-platform`/`commercial-catalog`
   directories, disabled by default in canary/production, and not reachable from any customer route.
   Enabling these does not expose anything to customers by itself (`TITAN_V200_RELEASE_AUDIT.md`
   §8) — they are internal experimentation/testing switches.

## Rate limits and quotas

Configured centrally in `config/subscription_tiers.json` (the declared single source of truth —
`COMMERCIAL_READINESS.md` §1). Do not add or adjust tier limits in `revenue-enforcement.js`,
`usage-meter.js`, or `workers/revenue-engine/` directly — that file already has one confirmed
drifted duplicate (`COMMERCIAL_READINESS.md` §1); adding a second edit surface would make the
problem worse, not better.

## Monitoring your instance

- `/api/health` — public, no auth, checked by every deploy/rollback workflow.
- `data/health/sla_status.json`, `runtime_health.json`, `ops_status.json` — generated by scheduled
  automation (`scripts/sla_engine.py` and related), not administrator-triggered.
- Alerts arrive via **Telegram only** today (`OPERATIONAL_READINESS.md` §2) — if your organization
  needs Slack/PagerDuty/email alerting, that integration does not exist yet despite being described
  in `docs/BCP_DISASTER_RECOVERY.md`; do not assume it is configured.

## Backups and restore

Daily automated (01:00 UTC): all 4 KV namespaces + R2 snapshotted (`scripts/backup_kv_to_r2.py`,
`backup_r2.py`, run via `automated-backup.yml`). Restore: `scripts/restore_kv_from_r2.py`. No D1
backup exists because no D1 database is part of the actual deployment.

## Rollback

`enterprise-rollback-governance.yml` — manual (`workflow_dispatch`), requires typing `CONFIRM`,
performs a git-revert + retag + post-rollback canary check + Telegram notification. Also available:
`scripts/rollback_authority.py` for snapshot/register/rollback/validate/history operations outside
the GitHub Actions UI. There is no automatic rollback-on-failure — a human must trigger this.

## Security posture you are responsible for reviewing before GA

`SECURITY_CERTIFICATION.md` in full — in particular, the 12 unauthenticated `/api/v1/p34/*`
endpoints and the wide-open CORS policy are platform-level decisions, not something an individual
administrator can mitigate through configuration alone; they require an engineering fix.
