## 1. Tiers — real enforcement, one clear single-source-of-truth violation

`config/subscription_tiers.json` is explicitly self-declared as authoritative: *"THIS IS THE SINGLE
SOURCE OF TRUTH for all subscription tier definitions... DO NOT duplicate tier definitions in Worker
CONFIG or frontend."* It defines real, detailed FREE/PRO/ENTERPRISE/MSSP tiers with concrete
differentiators (FREE: 100 calls/day, no STIX/AI/IOC visibility; PRO: **$49/mo**, 5,000 calls/day,
STIX + partial AI + IOC visible + dark web + CSV export). This is consumed live: `TIERS` constant +
`enforceTierGate()`/`applyTierGateV2()` (`revenue-enforcement.js`, imported at `index.js:95`) gate
real capabilities per tier in the live request path.

**Independently confirmed violation of the file's own mandate**: `workers/revenue-engine/src/index.js`
defines its own separate `TIERS` constant (line 1426) with **PRO at $99** — exactly double the
canonical $49 — plus two further inline price tables within the same file (lines 2213, 2242,
`{FREE:0, PRO:99, ENTERPRISE:999, MSSP:1999}`). This is a direct, concrete Single-Source-of-Truth
violation (CLAUDE.md Principle 3) with real commercial consequence: a customer or partner reading
`revenue-engine`'s pricing logic sees a different number than what `config/subscription_tiers.json`
(and the live Razorpay checkout, confirmed charging $49 for PRO) actually charges. **This is the
single most concrete, fixable defect in this entire commercial readiness review** — resolving it
means deleting `revenue-engine`'s duplicate tables and reading from the canonical file, not a
redesign.

## 4. Licensing

**Minimal.** `agent/license_validator.py` (47 lines) is a simple JSON-file-backed key validator
(`data/sovereign/tenants.json`, checks `status == "active"` and expiry) — no confirmed caller wiring
it into a live Worker request path in this audit. `LICENSE.txt`/`COMMERCIAL_LICENSE.md`/`eula.html`

from API-key tier gating, which does the practical work today) is effectively not implemented.

## 5. Upgrade flow — real, with two documented live defects

`upgrade.html` is a fully built, live plan-selector/checkout page (Razorpay + Gumroad integration).
Server-side upsell CTAs are generated by `buildUpgradeTrigger()` in `revenue-enforcement.js`,
embedded directly in gated API responses — a real, functioning upsell loop, not just a static page.

Two specific defects, both previously documented by the platform's own first-party audit
(`docs/BILLING_ENTITLEMENT_ARCHITECTURE_AUDIT.md`, 2026-08-03) and independently corroborated in
this pass:
- **The trial endpoint 404s from its own promoted URL**: `POST /api/leads/trial` only works on
  `revenue.intel.cyberdudebivash.com`, but nothing on the live site links to `/trial` at that host —
  the promoted trial funnel does not resolve.
- **`provisionApiKey()`'s revenue-integrity fix ships disabled by default** — see §6.

## 6. Revenue-integrity finding: a real fix exists, but isn't active in production by default

`provisionApiKey()` (`index.js:2421-2443`) previously hardcoded `expires_at: null` on every
provisioned key — meaning a single one-time Razorpay Order or Gumroad sale granted **permanent**
API access regardless of the monthly/annual price actually paid. This has been found and given a
real, deliberate fix (tagged `P2.7-001`, "shadow-mode expiry," independently verified in code):
`resolveAuth()` already correctly checks `expires_at` and downgrades to FREE when it's past — the
fix computes the real expiry and audit-logs it, but **only actually writes it to the key record
when `env.SUBSCRIPTION_EXPIRY_ENABLED === "true"`**. Independently confirmed:
`wrangler.toml` sets `SUBSCRIPTION_EXPIRY_ENABLED = "false"` at both the top-level and
`[env.production]` blocks. **Unless this has been manually overridden in the live Cloudflare
dashboard (not verifiable from this repository), every API key provisioned today still grants
permanent access from a single payment.** This is flagged as a genuine revenue-integrity gap, not a
security vulnerability in the traditional sense — but it is exactly the kind of finding a commercial
readiness certification exists to catch before GA, since it directly undercuts the tier/billing
model this whole document otherwise certifies as real.

## 7. Billing integration

Two live payment paths, one dormant:
- **Razorpay: real and live.** `upgrade.html`'s `initiateRazorpayCheckout()` calls a confirmed-live
  endpoint (`POST /api/payment/razorpay/create-order`, verified against production per
  `docs/BILLING_ENTITLEMENT_ARCHITECTURE_AUDIT.md` returning real 200 order responses). A
  subscription webhook exists (`workers/revenue-engine/src/subscription-engine.js`,
  `/api/v2/billing/webhooks/razorpay`) but is **"correct, dormant"** per the same audit — checkout
  only creates one-time Orders, never a Razorpay Subscription object, so the webhook path never
  actually fires.
- **Gumroad: real and live** — direct purchase links (`cyberdudebivash.gumroad.com`), webhook-driven
  key auto-provisioning.
- **Stripe: coded but unconfigured.** `scripts/stripe_billing_engine.py`, `stripe_webhook.py`,
  `stripe_revenue.py` and API-side handlers all exist, but the platform's own audit
  (`GODMODE-REVENUE-AUDIT-REPORT.html`) states plainly: payment-link environment variables are not
  configured and "Zero automated revenue flow" exists through this path.
